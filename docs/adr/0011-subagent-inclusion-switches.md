# 子代理计入:两个开关默认「等于现状」,红点的「开」才是旧行为

## Status

accepted

## Context

需求是"子代理与队友(teammate,会话标记上与子代理同源)的活动,算不算到父会话头上"。红点与黄点各问一遍,所以做成两个独立开关,默认都为 true;缺项或脏值一律回落 true。

动手前需要说清的两条事实:

1. **红点本来就会被子代理间接点亮。** 子代理结算会唤醒父会话,那一轮 `turn/end` 带着一条来源为子代理的 user 消息;既有行为照常给它亮红点。所以红点侧「开」**不是新功能,而是升级前的现状** —— 语义与直觉相反:「关」才是新行为,它要额外屏蔽掉这一部分。
2. **黄点的旧行为是完全跳过子代理。** 官方侧栏本就不显示 `origin === "subagent"` 的会话行,既有的黄点口径也把它们排除在外。于是黄点侧默认「开」意味着**升级后黄点会开始因子代理而亮**,这是一次用户可见的行为变化,必须有意承认,而不是假装兼容。

## Decision

**两个开关各自独立、默认 true,并且默认值一律取「等于现状」或「有意承认的变化」。**

- **红点:`unreadIncludeSubagents`(客户端回落常量同名)。** 开 = 既有行为,子代理结算唤醒父会话产生的未读照常亮;关 = 屏蔽"由子代理引起"的未读。判据放在宿主折叠 `turn/end` 时:该回合**第一条 user 消息**的来源是子代理结算或代理消息,就给该 `turn/end` 打 `subagentCaused` 标记,客户端在开关关闭时跳过这些会话。
- **黄点:`includeSubagents`(客户端回落常量同名)。** 开 = 某会话的子会话正在 running 时,沿 `parentSessionId` 上溯到最顶层非子代理祖先,把该祖先计为「进行中」;**多个子代理归属同一祖先只算一次**(数字仍是会话数);子代理自己的行不亮;祖先自身的等待交互语义不变。关 = 完全等于旧行为(跳过所有 `origin === "subagent"` 行)。
- **队友一并覆盖**:DSH 里 teammate 与 subagent 在会话标记上同源,不为它们另立口径。
- **落盘的永远只是偏好**,不是"谁在跑"或"谁产生了未读";两项缺项/脏值都回落 true,老配置不需要迁移。

## Consequences

- **黄点默认开 = 有意的可见行为变化。** 升级后,后台有子代理在跑会让父会话那一行、工作区数字与标签页黄标记亮起。这不是 bug,但有变成噪声的可能;觉得吵的用户需要自己去关。选择默认开,是因为"看不见子代理在替自己干活"通常比"多亮一个黄标记"更糟。
- **红点的归因是近似,边界是明确的:一个回合只取第一条 user 消息定归属。**
  - 子代理唤醒的那一轮里**人中途插话** → 整轮仍被判为子代理引起 → 开关关闭时该轮结束**被误屏蔽**(少亮一次)。
  - 人发起、子代理中途 steer 进来的回合 → 判为人发起 → **不屏蔽**。
  - 误屏蔽的后果是"该亮的没亮",不会丢数据、不会漏事件,且只发生在开关**关闭**时;默认开的状态下不存在这个边界。
- **红点语义反直觉是刻意的代价。** 「开 = 计入 = 旧样子」保证升级后行为不突变;把开关名与说明写成"计入子代理"而不是"屏蔽子代理",是为了让默认值读起来是"打开某个能力",而不是"打开了某个遮挡"。
- **黄点数字仍是会话数。** 多个子代理归属同一祖先只算一次,所以一个祖先带十个子代理,数字仍是 1,不会因为子代理数量而膨胀。
- **黄点不依赖红点那套宿主投影**,红点开关也照旧独立:关掉任意一个,另一个的行为与显示都不变。

## 备选方案(未采用)

- **红点开关语义倒过来(开 = 屏蔽子代理)。** 与既有行为相反,升级瞬间就是行为突变,默认值无法取"等于现状"。
- **两个开关都默认 false。** 升级后红点会突然少亮一批、黄点也不再因子代理亮起,用户不主动打开就永远回不到升级前的样子。
- **黄点不追溯祖先,直接给子代理自己亮。** 子代理不进侧栏,没有可亮的行;给父会话亮才是唯一能被看见的做法。
- **红点按整轮所有 user 消息判定来源。** 更"准",但要保留整轮来源集合;而且在"子代理唤醒 + 人中途插话"这种混合轮里,"算不算子代理引起"本身没有唯一正确答案,却要多付一份状态。
